# 行政系統名冊同步 v1 Spec

## Verdict

Decision：**行政系統（webSystem）是組織資料的上游真相**。孩子是誰、在哪一班、老師帶哪
一班，這些事實由行政系統決定；相本系統只鏡射，**永不回寫**。相本系統自己擁有的是相本、
工作格、相本稱呼（`students.album_name`）與主管指派。

Decision：**先做唯讀的漂移報告，再做寫入**。在看得見漂移之前不動任何資料——報告本身
就是同步邏輯的八成，而且零風險。

Decision：異動**分兩類**：安全的自動套用，會改變權限或撞上已知死結的進待審佇列。
不是所有「上游說了算」的事都適合在無人看管時直接落地。

Decision：資料來源是**定時的一致性快照**（`sqlite3 .backup`），不掛載上游原檔。
webSystem 是 SQLite + WAL、10 個 uwsgi worker 共用，唯讀掛載會失敗（WAL 的讀取者需要
寫 `-shm`），而直接連原檔會跟正式流量搶鎖。

Decision：**學期編班不在本 spec 範圍**。套用編班會關閉舊學期、結束所有名冊與編制，
不可逆；上游的下學期資料是逐步輸入的，自動套用等於把「什麼時候切換」這個需要人判斷的
決定交給排程。編班維持
[term-scoped-classroom-v1](term-scoped-classroom-v1.md) 的草稿→驗證→套用流程。

## Problem

相本系統的組織資料是 **2026-07-17 遷移當天的一次性快照**，之後沒有任何機制讓它跟上：

```
classroom_members 建立時間
  2026-07-17   465 筆   ← 遷移
  2026-05-27     1 筆
有結束紀錄的成員：departed 1 筆
```

同一期間行政系統記了 **76 件**期中異動（114 下學期，約半年）：

| 事件 | 件數 |
|------|------|
| 期中入班 | 37 |
| 期中離班 | 15 |
| 期中老師異動 | 20 |
| 期中換班（升班） | 4 |

約每月 12 件。相較之下學期轉換一年只有 2 次——**日常維運才是重複輸入的主要來源**，
而且漂移的後果全都不會報錯：新生沒有相本、已離園的孩子被做了相本、升班的孩子在錯的班。

2026-08-02 抽查時兩邊 100% 吻合，那是因為遷移剛好抓在期末、之後兩週剛好沒事發生，
**不是因為有機制維持**。

2026-08-04 再抽一次就看得到了：距上次僅兩天，上游多了 2 筆入班、1 筆老師編制、
1 個班改名。而以 115 上開學日（8/1）為基準是 402 位在籍，以 8/4 為基準已是 **423 位**
——**開學後三天就有 21 位孩子的入班日到期**。相本系統這邊完全不知道。

## Scope

- 名冊孩子：新建、姓名更正、學號回填
- 班級成員：期中入班、離班（`classroom_members` 的區間）
- 老師編制：`classroom_teachers` 的新增與結束（**只列出，不自動套用**）
- 漂移報告：可獨立執行、唯讀、可排程

## Non-Goals

- 不回寫行政系統
- 不自動套用學期編班（見 Verdict）
- 不同步相本稱呼（`album_name` 是相本系統自己的欄位，上游沒有這個概念）
- 不處理期中換班造成的重複相本——那不是同步問題，是相本的學生集合被凍結、缺少轉出
  入口，現況與限制見
  [known-issues.md 的期中轉班](../dev/known-issues.md#開放設計問題)

## 對應鍵

三條鍵在 2026-08-02 逐筆驗證過，全部 100% 對得上：

| 實體 | 相本系統 | 行政系統 | 驗證 |
|------|----------|----------|------|
| 孩子 | `students.student_serial` | `student_student.studentSerial` | 466/466，且在籍 465 位的班級與上游完全吻合 |
| 老師 | `users.username` | `personnel_staff.staffSerial` | 65/65，姓名一字不差 |
| 班級 | （分校名＋班名） | `school_campus.name` ＋ `school_clas.name` | 37/37 |

**姓名永遠不可以當鍵**：行政系統用姓名後綴 `.` / `*` 區分同名不同人（實例：三個郭芯妍、
兩個陳又愷）。學號才是唯一且穩定的識別。這條規則的由來見
[data-model.md](../dev/data-model.md)。

**學號與員編是兩套獨立的序號空間，而且字面大量重疊**：2026-08-04 對正式資料實測，
**430 個序號同時是某位學生的學號、也是某位不同職員的員編**（`DN0022001` → 學生王品淯
／職員邱惠萍）。所以上表三條鍵必須各自成對比對，任何「先用序號找人、再看他是學生還是
老師」的寫法都會把不相干的兩個人湊成一對，而且不會有錯誤訊息。由
`test_student_serial_and_staff_serial_are_separate_namespaces` 釘住。

班級的對應鍵是名稱組合而不是上游 id，是本版的**已知弱點**：上游改班名會被看成「新班」。
v1 以「班級異動一律進待審佇列」迴避；要根治需要在 `classrooms` 上加 `external_id`，
留待 v2。

這不是理論風險——2026-08-03（115 上開學後第三天）上游就把 `school_clas` id=649 從
「湖美校／五階B」改成「湖美校／四階B」（年級 5→4，部門仍是嬰幼），班上 5 位學生與
1 位主教跟著搬。以名稱為鍵時，這一筆會被讀成「五階B 整班消失、四階B 整班新增」。

## 資料取得

1. 排程在正式主機上對 `~/production/webSystemCompose/webSystem/db.sqlite3` 做
   `sqlite3 .backup`，輸出到相本系統容器讀得到的共用位置
2. 同步作業只讀那份快照，不碰原檔
3. 快照時間戳寫進稽核紀錄——每一次同步都要能回答「依據哪一刻的上游狀態」

兩個系統的容器都在 Docker 網路 `nginx_net` 上，上游資料庫沒有對外開埠，不需要為此
暴露任何服務。

## 同步分類

| 自動套用 | 進待審佇列 |
|----------|------------|
| 新生建檔並編入班級 | 該生有**製作中**相本卻在上游被標離園 |
| 姓名更正 | 期中換班（會撞上重複相本的死結） |
| 學號回填 | **老師編制異動** |
| 離園（該生**沒有**製作中相本時） | 單次異動超過爆炸半徑上限 |

老師編制之所以不能自動套用：`classroom_teachers` 同時決定四處行為——
`project_access_service`（誰能編相本）、`project_assignment_service`（轉交負責人）、
`organization_scope_service`（主管範圍）、`teacher_overview_service`（進度報表）。
上游把老師從班上移掉，她會在製作到一半時瞬間失去編輯權，而且四個地方同時改變。

## 安全閘

1. **爆炸半徑上限**：單次同步若要改動超過在籍名冊的 5%，整批中止並告警。防的是上游
   快照損壞或對應鍵大量失效把名冊洗掉
2. **只寫目前學期**：已結束學期由 `trg_classroom_members_freeze_closed_term_*` 與
   `trg_classroom_teachers_freeze_closed_term_*` 保護，同步碰到它們就是 bug
3. **預設 dry-run**：`--apply` 才寫入，與
   [testing.md 的維運腳本慣例](../dev/testing.md) 一致
4. **稽核紀錄**：每次執行記下依據的快照時間、各分類的筆數、實際變更的列

## Implementation Slices

**Slice 1 — 漂移報告（唯讀）** ✅ 2026-08-02 完成

`scripts/report_websystem_drift.py`：讀快照與相本資料庫，輸出分類後的差異清單與統計。
不寫入任何資料。規則由 `tests/test_websystem_drift_report.py` 釘住。

首次執行結果（基準日 2026-07-31，即 114 下期末）：**漂移 0 筆**。相本系統自 7/17 遷移
以來沒有落後——因為遷移剛好抓在期末、之後兩週沒有異動，不是因為有機制維持。

偵測能力另以「基準日 2026-03-01」驗證過：對同一份相本資料庫，正確找出 15 筆應離園、
1 筆應入班、3 筆期中換班、8 筆編制應新增、7 筆應結束，並觸發 5% 爆炸半徑警告（9.2%）。
一個回報 0 的偵測器必須另外證明它抓得到東西。

實作時修掉一個誤判：行政系統用姓名後綴（`.` `*` `．`）標記同名不同人，第一版把它們當成
4 筆「姓名不符」。照那樣同步會把「陳又愷.」寫進相本系統並印在相本上。比對前一律剝除，
但不能連真的改名一起吃掉（2026-08 就更正過 31 筆打錯的姓名）——兩者都有測試。

**Slice 2 — 自動套用** ✅ 2026-08-02 完成（待審佇列改為只列出，見下）

`scripts/sync_websystem_roster.py`：在 Slice 1 的比對之上加寫入，預設 dry-run。
自動套用新生建檔與入班、補在班區間、姓名更正、離園；其餘只列出、不動。

在正式資料副本上以「基準日 2026-03-01」實測（該基準日對現況刻意製造出差異）：

| | |
|---|---|
| 自動套用 | 15 筆（新生 9、補入班 1、離園 5） |
| 只列出 | 28 筆（換班 3、離園但有製作中相本 10、編制 15） |
| 在籍 | 465 → 470（+10 入班 −5 離園） |
| 名冊 | 592 → 601（+9 新生） |
| 外鍵檢查 | 無違規 |
| 再跑一次 | 自動套用 0 筆（冪等） |

**15 筆離園裡有 10 筆因為該生有製作中相本而被擋下**——那正是這道分類要防的事。

**待審佇列（表 + UI）暫不實作**：實測一個學期只有 20 筆編制異動、4 筆換班，約每月
3 筆。為每月 3 筆蓋一張表加一個管理介面不划算；先由報告列出、人工在既有的園所設定頁
處理。等實際頻率或處理延遲證明需要，再回頭補。

**Slice 3 — 排程**

**頻率：每天一次，離峰時段（約 02:00）。** 依據是實測的異動量——一個學期 76 件、
約每月 12 件，多數日子是 0 件；每小時跑只會產生大量空轉。而延遲的代價可以接受：
孩子週一入班、隔天早上就在名冊裡，老師還沒開始做他那一頁。

每次執行的順序（都在正式主機上，albumMaker 與 webSystem 是兩個 compose）：

1. `docker exec production_websystem_web python -c "…backup…"` 產生一致性快照
   （不直接讀原檔：WAL 模式下會跟 10 個 uwsgi worker 搶鎖）
2. `docker cp` 把快照送進 albumMaker 的 app 容器
3. `docker compose exec app python scripts/report_websystem_drift.py …`
4. `docker compose exec app python scripts/sync_websystem_roster.py … --apply`
5. 刪掉兩邊的快照暫存

三支腳本必須在 image 裡（Dockerfile 是逐檔列舉，不是整個 `scripts/` 目錄）。

**分兩階段開啟**：

- **階段 A（可以先做）**：只跑第 3 步的報告，不加 `--apply`。零風險，而且立刻讓漂移
  可見——目前沒有人知道相本系統跟行政系統差多少。
- **階段 B**：確認有人真的在看報告、而且通知管道已配置之後，才加上 `--apply`。
  在沒有人看的情況下開啟自動寫入，等於讓資料無聲改變而沒有任何觀察者。

通知管道本身是
[known-issues.md 的營運缺口](../dev/known-issues.md#營運缺口依風險排序2026-07-13-記錄)
第 2 項，尚未配置——階段 B 卡在它。

## Risks And Test Plan

| 風險 | 緩解 | 測試 |
|------|------|------|
| 上游快照損壞導致名冊被洗掉 | 爆炸半徑上限 | 給一份「大量對不上」的快照，驗整批中止且無寫入 |
| 對應鍵碰撞（同名不同人） | 只認學號 | 用行政系統真實的同名資料（郭芯妍 ×3）驗不會混 |
| 同步碰到已結束學期 | freeze trigger | 驗寫入被 trigger 擋下並回報 |
| 老師被移除導致製作中相本失去編輯權 | 進待審佇列 | 驗有製作中相本時不自動結束編制 |
| 重複執行造成重複建檔 | 以學號查既有名冊項 | 連跑兩次，第二次應為全 0 |

## Acceptance Smoke

在正式資料副本上跑一次 Slice 1，人工核對報告中的新生／離園／換班與行政系統一致；
再跑 Slice 2 的 `--apply`，確認：在籍人數變化等於報告的預期值、已結束學期未被改動、
稽核紀錄完整、重跑第二次為全 0。
