# 文件維護規則（Doc Policy）

> 本檔是「文件該怎麼寫、怎麼改、怎麼拆」的唯一真相來源（SSOT）。
> 各主題的內容歸屬見 [CLAUDE.md 的文件地圖](../../CLAUDE.md#文件地圖)。

---

## 核心原則：每個事實只有一個家

每一條規則、數值、慣例、注意事項，都只允許完整存在於**一個檔案**（它的 owner）。
其他檔案需要提及時，**用連結，不复述**：

```markdown
渲染補償細節見 [rendering.md 的陰影補償](rendering.md#陰影補償shadowblur--174)。
```

判斷落點的方法：查 [文件地圖](../../CLAUDE.md#文件地圖) 的「owns」欄。
如果新知識不屬於任何現有檔案，**先改地圖**（新增檔案或擴充 owns 範圍），再寫內容。
地圖與實際內容衝突時，以地圖為準修正內容。

## 允許的例外：捷徑複本

高頻使用的短內容（如啟動指令）允許在別處放複本，但**必須緊跟 SSOT 標記**：

```markdown
> SSOT: [README.md#快速開始](../../README.md#快速開始) — 此處為捷徑複本，衝突時以 SSOT 為準。
```

沒有標記的重複內容視為 bug，發現時刪除複本、留下連結。

## 引用程式碼：用符號，不用行號

行號會隨每次 commit 腐爛。引用程式碼一律用「檔名 + 函式/類別/常數名」：

- ✅ `draw_helpers.py` 的 `add_drop_shadow()`
- ❌ `draw_helpers.py:122`

例外：引用「某一行的具體字面值」且該檔極少變動時可以加行號輔助，但符號名仍必須在場。

## 錨點穩定性

跨檔連結依賴 heading 錨點。改任何 heading 前，先全案搜尋舊錨點：

```bash
grep -rn "舊標題關鍵字" *.md docs/ frontend/README.md
```

heading 命名習慣：條目型知識用「名詞：結論」格式（如「陰影補償：shadowBlur × 1.74」），
讓連結文字本身就能傳達內容。

## 文件與程式碼同 commit

改動程式碼若使某條文件敘述失真，**同一個 commit** 內更新該敘述的 owner 檔案。
不確定哪些文件受影響時：`grep -rn "<函式名或關鍵字>" docs/ CLAUDE.md README.md`。

## 拆分規則（文件長大時）

單一檔案超過約 **300 行**，或某一節被 3 個以上檔案引用時，把該節拆成獨立檔案：

1. 新檔案加入 [文件地圖](../../CLAUDE.md#文件地圖)，宣告 owns 範圍
2. 原位置留一行 stub 連結（保護既有連結），下次大改時移除
3. 全案搜尋舊錨點，更新所有引用

## 過時與未定案內容

- 已知的程式碼／文件落差（drift）、尚未決定的設計問題，統一記在
  [known-issues.md](known-issues.md)，不散落在各主題檔
- 修掉一條 drift 時，同 commit 從 known-issues.md 刪除該條

## 新 agent 上手動線（設計意圖）

1. `CLAUDE.md` 每次 session 自動載入 → 得到硬規則 + 文件地圖
2. 依任務主題，只讀對應的 1–2 個 `docs/dev/*.md`（每檔皆 < 300 行）
3. 深入某模組時再讀程式碼本身

因此 CLAUDE.md 必須保持**薄**：只放 agent 行為規則與地圖，任何領域知識都不放。
